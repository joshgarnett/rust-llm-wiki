2026-09-28. Independent source/design review against accepted P16 `cbaf990bfbc35f8e12ffe0396d3e65c814eab34b`; P17 implementation is not accepted by this report. Reviewed the selected P17 contracts, `P17-plan.md`, and the existing catalog, eligibility, provider configuration/dispatch/wire, and job receipt/replay boundaries. ## Assessment of the proposed plan

The proposed split between rendering, spaces, vectors, fusion, and application orchestration is workable. Freshly rendered membership joins, omission of ineligible descriptions, and retaining an old active space during replacement are the right foundations. The following are concrete integration obligations, not findings that accepted P16 is defective. Resolve them in implementation and local fixtures before P17 acceptance.

### D1 — Membership proof must survive the application's own receipts

`catalog/snapshot.rs::verified_snapshot` compares the entire current projection. `catalog/scan.rs::project` includes every canonical Markdown note in projection dependencies; run and usage-receipt records also appear as documents. `catalog/publish.rs` advances generations for canonical changes and `catalog/sql.rs::prune_generations` removes old generations. Therefore a response's receipt can invalidate the starting generation/control manifest even when its rendered corpus input is unchanged.

Use two distinct bindings: a stable expected target/unit/input/eligibility/dependency fingerprint captured before dispatch, and the freshly verified catalog generation to which membership is attached. Under the writer permit, re-render after remote I/O and after receipt-induced publication. Activate only exact matching stable bindings in that fresh generation; a source edit cannot become valid merely because the application re-rendered a new generation. Preserve old input blobs without activating stale memberships. Recheck the control manifest as well as known dependencies to catch newly introduced duplicate IDs/decisions. Do not weaken this to file timestamp checks.

Memberships in a separate SQLite cache must also bind parser/control identity, not the generation integer alone: deleting/rebuilding the catalog can restart generation numbering. A pinned reader can outlive publication, so semantic lookup must use the reader's complete binding consistently.

Exclude operational run/receipt/event bookkeeping from the semantic corpus target set explicitly. Otherwise every embedding receipt creates another missing document vector and replacement coverage need not converge. This is a target eligibility decision, not a reason to remove those records from canonical scans.

### D2 — Space identity is narrower than provider/accounting identity

`config/providers.rs::service` computes its fingerprint from authentication references, rate card, timeouts, batch limits, tokenizer and other settings as well as model/endpoint. `ServiceSummary::profile_fingerprint` incorporates that service fingerprint. Neither that fingerprint nor `config_fingerprint` can stand in for `SpaceId`: changing credentials or pricing must not create a new embedding space.

Hash a versioned canonical structure containing the sanitized endpoint/profile identity, requested model, explicit deployment revision, configured dimension (`auto` remains `auto`), metric, query/document role options and exact prefixes, normalization policy and render version. Keep actual dimension separate and establish it atomically only from a completely valid corpus batch. A check probe or first query cannot establish it. Reject a conflicting later batch as a whole. Batch retries or racing corpus batches cannot overwrite an established dimension. Retain returned model metadata for validation/diagnostics without treating an alias as proof of deployment stability.

The accepted embedding wire sends only model/input/float encoding/optional dimensions. If role options imply additional wire behavior, reject unsupported options until the adapter implements and fingerprints them; hashing an ignored option is not implementation. Ensure identical text in distinct effective query/document roles cannot share a cache row incorrectly. Prefix-only roles can safely reuse a row when their actual rendered input bytes are identical.

### D3 — Retained configuration is data, never renewed authority

`ProviderConfig::authorize` authorizes the current configured profile service; `TrustedService::recheck` binds private file content, vault root/marker and CA. The suggested `authorize_retained_embedding` helper needs a precise authority rule before implementation. Safest bounded interface: locate an independently currently authorized service whose semantic wire identity exactly matches the retained space, use its current credentials, then dispatch the retained query prefix/render configuration. If no matching service remains permitted, a matching cached query may work; otherwise return semantic unavailable. Do not mutate the newly authorized service's model/endpoint into old values based solely on cache metadata.

If supporting reconstruction from retained endpoint/model configuration, define and test the private trust rule that explicitly authorizes that retained endpoint and configuration. Endpoint fingerprint alone cannot reconstruct an URL or confer permission. Credential rotation may be allowed without changing space, but revocation cannot be bypassed by a retained `TrustedService` or cache metadata.

The active pointer must remain old during incomplete replacement. Re-render eligible current inputs using the old retained renderer/prefixes and intersect them with old vectors; changed inputs and invalidated descriptions are missing coverage, never stale hits. Compute candidate-space coverage against the same freshly verified target universe and switch the pointer atomically only after the required coverage passes. Do not accidentally read the new profile to generate an old-space query, even when dimensions match.

### D4 — Cache storage is disposable and publication is not cross-store atomic

The worker proposed a separate SQLite cache in coordination; use the repository's `.wiki/cache/` namespace, not `.lwiki/cache/`. Document whether deleting `index.sqlite` alone or all `.wiki/cache` causes vector loss, and make diagnostics follow actual cache state. A separate cache avoids adding new tables to the existing generation-pruning sequence, but does not create a cross-database transaction.

Store vectors by exact `(space,input_hash)` with little-endian normalized float32 bytes and a hash of those exact stored bytes. Normalize using float64 accumulation, then validate the stored float32 result, dimensions and nonzero finite norm. Read validation must reject malformed lengths, wrong dimension, NaN/infinity and zero norms; corruption is unavailable coverage, not score zero. Compute cosine with float64 dot/norm over those stored float32 coordinates.

Write cache blobs before advertising receipt refs to them. Membership/pointer updates need an atomic cache transaction and a fresh canonical proof under the existing writer discipline. Crash/replay must distinguish a durable blob from activated current membership. Never infer current membership or vector existence from a Markdown receipt. A lost settled vector stays missing until explicit embeddings sync authorizes replacement; index rebuild performs no remote work. If a valid uncommitted paid response spool still exists, deterministic re-materialization can avoid a repeat paid request, but the receipt alone cannot reconstruct it.

### D5 — Implement the actual Received → receipt → settle → vector task sequence

`providers/dispatcher.rs` returns a valid `DispatchOutcome` while its attempt is Received. Its default materialization plan is not a validated vector-output receipt. The crate-private `jobs::checkpoint::receipt_plan` is the correct existing mechanism to bind `OutputDisposition::Validated` and exact `VectorCacheRef` values. Each ref includes space, input, normalized blob hash, dimensions and membership fingerprint. Commit that canonical plan through `ChangeEngine`, call `outputs_committed` with precisely those refs, then settle. Inspect an existing immutable receipt on replay instead of regenerating different receipt bytes.

`jobs/checkpoint.rs::receipt_plan_locked` attaches source/scope read preconditions to validated receipts; these will deliberately fail after a source edit during HTTP. Define the stale-paid-output path explicitly: retain accounting with a rejected/unknown receipt without activating output refs, or another supported truthful disposition that does not bypass freshness guards. A `FreshnessConflict` must not discard paid attempt/spool identity or cause an automatic fresh send. Unknown usage remains unknown after settlement.

`jobs/ledger.rs::repair_task_finish` deliberately skips automatic completion for cache-bearing receipts. P17 must verify cache refs and use the existing explicit completion path after settlement; generation/task completion cannot be inferred from a vector count. Conversely, a stale/rejected response must not complete the intended corpus task.

Existing `replay` reports cache refs as unverified/missing and does not validate this new cache. Existing `Dispatcher::execute` rejects a new send while a prior response lacks a receipt. There is no public retained-response decode API. Request a narrow root-owned replay/materialization helper that reuses sealed P16 input/response validation rather than parsing provider JSON differently in P17. Replay must reconcile cache hashes, receipt commit, acknowledgment, settlement and task completion independently. Preserve the paid failure object until these obligations are retained or surfaced; extracting only `failure.error` can erase useful recovery identity.

## Minimal acceptance checklist

1. Change each required space field independently, including equal-dimension model/revision/prefix changes; spaces stay isolated. Change credentials/rate card/timeout without changing representation; space stays stable. Fixed and auto dimensions obey corpus-only establishment.
2. Begin corpus embedding; edit same-size/same-timestamp source, rename assertion endpoint, introduce duplicate ID, or withdraw support before response. No stale membership activates. Paid response still obtains conservative durable accounting. A normal response/receipt generation advance does not falsely reject unchanged inputs.
3. With one support remaining, assertion is current; after final support withdrawal it cannot seed semantic results. Entity identity can remain searchable while its stale description never contributes. Repeated identical query-cache hits still rerun corpus eligibility/freshness checks.
4. Keep old active space while replacement is partial. Unchanged current inputs remain usable with accurately partial coverage; changed inputs are absent. Query with retained old prefixes/model under matching current trust. New-model query, revoked trust, or unreproducible old configuration cannot score old vectors; exact cached old query follows the documented offline rule.
5. Known vectors give deterministic float64 cosine order and target/unit ties after float32 storage. Malformed/corrupt blobs are omitted and reduce coverage. Scan and top-k allocation stay bounded; filters are applied before scoring/caps.
6. Interrupt after spool, blob commit, receipt commit, acknowledgment, settlement and before membership/task completion. Replay never sends again merely to recover a valid retained response, never settles twice, and never marks missing/corrupt cache output complete. Delete disposable cache and rebuild canonical index: receipts survive, missing coverage is explicit, and no implicit embedding occurs.
7. Source edit during a paid query or between dense scoring and final result emission causes reproof/retry or explicit unavailable/unverified behavior under the existing contract. Binding only before remote query I/O is insufficient.
8. Offline cache miss/dry run does not invoke credentials, dispatcher or remote probes; successful earlier batches and their receipts survive a later invalid batch or budget stop. Replacement pointer stays unchanged on incomplete coverage.

These are source-derived design gates. This report makes no native crash-safety, power-loss, hostile concurrent filesystem, or live-provider compatibility claim.

### R1 — Recovery errors must not irreversibly reject valid paid output

**Actionable shared-helper finding.** `providers/dispatcher.rs::recover_response` maps every `decode_retained` error to `DispatchDisposition::Rejected` and attempts to create an immutable rejected receipt. But `decode_retained` also returns errors for a missing/changed retained task descriptor, a mismatched currently supplied sealed service contract, missing spool bytes, a body/metadata hash mismatch, and operational locking/read failures. None proves that the originally retained provider output was invalid. A valid response can become recoverable again when the correct service/descriptor is restored; an already committed rejected receipt prevents later validated materialization with different bytes. The P18 caller commits any returned materialization plan, so this distinction affects actual behavior, not just a diagnostic label. The existing wrong-model test calls `decode_retained` directly; it does not establish `recover_response`'s receipt behavior.

**Minimal fix:** classify errors structurally at the retained decode boundary. Failures before a fully hash-bound response and exact retained wire descriptor are established should preserve the attempt and any known spool, expose no rejected materialization plan, and require recovery without resend. Only a proven provider rejection or decode/schema/contract failure from those bound bytes should offer a rejected receipt. Do not infer this distinction from broad `ErrorCode` values: descriptor validation and response decoding can share codes. A small internal `RetainedDecodeFailure::{Recovery, InvalidResponse}` or equivalent phase-structured result is sufficient. Keep source freshness separate: successful decode may survive a source change, while activation still fails its source guards.

**Focused checks:** wrong supplied service, temporarily missing descriptor, temporarily missing body, and changed body hash must leave no new rejected receipt and must preserve the original paid attempt. Restore correct inputs/bytes and recover successfully with zero transport calls. Separately, a hash-bound malformed response must retain a rejected receipt and its paid accounting. Exercise the public `recover_response` helper/caller, not just pure decode.

### Concrete orphan-spool adoption design

The actual existing machinery already has a useful path: `JobLedger::replay` enumerates owner-bound spool directories; when both body and metadata exist, it verifies an existing attempt, the admitted body bound and metadata structure, and appends `Received` for an attempt still in `DispatchIntent` with no recorded spool. `OutcomeUnknown` leaves that phase unchanged, so it does not block adoption. Replay then refreshes observed usage/terminal/bound-violation accounting. P18 calls replay before choosing retained recovery. Merely calling `inspect`/`decode_retained` will not adopt an orphan, because `decode_retained` requires the recorded `SpoolRef`.

For P17, a narrow crate-private `JobLedger::adopt_retained_response(&AttemptRef) -> Result<Option<SpoolRef>>` can reuse the same internals without scanning every request directory or performing unrelated canonical replay. It should have exactly these properties:

1. Require local-write policy (dry run only inspects/reports), but allow offline accounting recovery. Enter `self.with(false, ...)` so changed source bytes do not prevent retaining paid accounting. Match the full attempt against loaded history and require the existing complete `SendAuthorized` binding in `state.sent`, just as normal `record_response` does. This parity check is an invariant for the new helper, not a claim of an ordinary crash path currently creating an unsent spool.
2. If a recorded spool already exists, read and verify it against its exact hashes/lengths and return it idempotently. Do not recreate a cleaned settled spool, replace existing bytes, or synthesize send authority. If no spool exists, adoption requires `DispatchIntent` and both durable files.
3. Read via `RunLedgerGuard::read_spool`, which authenticates canonical owner bytes binding vault/run/full attempt/request identity. Use the minimum of admitted response bound and capability hard spool ceiling (generation 1 MiB, other 8 MiB); metadata is at most 64 KiB. Strictly parse/validate `ResponseMetadata`, compute a `SpoolRef` from the actual bounded bytes, and do not guess status/usage from provider body when metadata is absent.
4. Insert that metadata into `received_meta`, append/fsync `Received` through the ordinary journal path, then `refresh_observations`. The ordinary append path already handles torn journal tails/head durability and recounts the new state. No vault writer lock, credentials, DNS, transport, or new reservation is needed or permitted during adoption. A failed append remains restartable; a durable Received with a stale head is already handled by the existing load/append rules.
5. Return only retained data, never a dispatch permit. The caller then invokes the common sealed `decode_retained`/`recover_response`, verifies current corpus inputs, commits a truthful receipt, acknowledges, settles, verifies cache refs and completes the task. Provider-invalid retained output still incurs accounting. Incomplete spool or unresolved intent remains conservatively unknown and must not silently fall through to a new paid request.

Both complete spool files become adoptable after `AfterSpoolMetadataSync`/`BeforeReceived`; after `AfterSpoolBytesSync` alone the response lacks complete retained metadata, so automatic successful materialization is unavailable. Do not promise no-repeat successful completion for that partial boundary; promise no automatic resend, honest unknown accounting, and retained evidence for reconciliation.

Minimal tests for this helper: complete orphan at `BeforeReceived` adopts/replays with zero transport calls; body-only orphan stays unknown; repeating adoption adds no second Received/settlement; changed owner or bytes cannot adopt as an already recorded different spool; a retained bound breach reconciles/pauses conservatively; a source edit still allows paid receipt retention while preventing active membership. Reuse the existing injected operational checkpoints; no new hostile-filesystem or power-loss guarantee is required.

## P17 changed-invariant implementation review

Bounded follow-up on 2026-09-28, limited to paid cache publication/recovery, retained-space queries, freshness and streaming. No source files, Cargo commands, Git operations or nested delegation were used. The authoritative query universe is the freshly rendered eligible-unit/filter intersection with exact `(space,input)` vectors; a physical SQL join to disposable persisted generation memberships is not required.

The following findings were communicated directly to the P17 worker and inspected after correction:

- **Paid cache readiness:** `app/embeddings.rs::dispatch_embedding_task` stages normalized vectors with `ready=0`. Exact receipt commit/acknowledgment and settlement precede `verify_vector_receipt`, then `confirm_refs`, completion and cleanup. The new receipt verifier reads the canonical receipt using its exact durable ref and requires the exact Settled attempt, Validated disposition and output/cache-ref agreement. It also runs on the OutputCommitted/Settled shortcut before confirmation; settlement's idempotent Settled return alone does not authenticate canonical receipt bytes.
- **Local recovery is not response rejection:** retained decode uses `RetainedDecodeFailure`, preserving local service/descriptor/spool/hash/lock failures. Materialization errors reject only actual vector/provider contract errors. A failed receipt commit with `FreshnessConflict` now causes rejection only after a new verified render proves affected targets changed. Otherwise it preserves the paid recovery path. Actual source/dependency changes still refuse current membership and retain paid accounting.
- **Descriptor binding during remote I/O:** the post-response cache materializer previously reread an unverified descriptor, allowing changed ordered input hashes to receive vectors generated for the original order before the later task binding failed. It now checks exact original byte length/hash and canonical serialization before any vector write. A descriptor mismatch remains recoverable Received, with no replacement rejected receipt. `descriptor_swap_preserves_paid_response_then_restores_without_send` is authored for this path; no current pass is claimed here.
- **Deletion after accounting:** the recovery sweep executes unconditionally before publication, including all-cache-hit syncs. Received/unresolved paid work still blocks replacement. OutputCommitted missing-cache work settles; already Settled missing refs can be skipped without invented task completion. Explicit replacement retires the already-accounted marker and creates new paid work while retaining old receipt/accounting history. The new regression currently checks replacement and two total calls; strengthen it to assert the old task stays unfinished and old receipt/hash/accounting remain unchanged.
- **Actual stored-vector proof:** `vectors.rs::verify_ref` uses the SQL-bounded blob reader, checks the actual space dimension, stored and computed normalized-blob hash, exact ref dimension and decoded finite/nonzero/unit-normalized values. It deliberately accepts staged rows for pre-confirmation verification. `confirm_refs` first verifies all refs and transactionally updates only matching space/input/hash/dimension rows; ordinary query access requires ready rows.
- **Atomic retained policy and final freshness:** same-SpaceId segmentation-policy preparation retains the active spec until complete coverage permits one transaction to update membership, spec and active pointer. Query scoring and final emission compare the full retained spec as well as SpaceId. Paid query misses must reproduce the active service/model/revision/dimension configuration and renew trust; cached query vectors need no new credentials. Lexical fallback now performs the same final verified-catalog comparison and one bounded retry. Runtime/application dry-run and offline policy disagreement is rejected before cache/index access on check, sync and query paths.
- **Streaming:** exact scoring retains bounded vector rows and top-k heaps; document and graph renderers now emit lazy segments borrowing the pinned catalog text. The frontmatter parser receives only a bounded envelope window, avoiding a full-document copy. Graph raw-span mapping is established once per description, then offset by each segment, eliminating the previous whole-note search for every segment. Complete corpus collection remains in explicit sync preparation, not the exact query scan.

Required qualification is still the worker's matching-source targeted suite plus root integration gates. The earlier twelve-test P17 result predates these changes. In particular, test staged rows cannot score before receipt/settlement, complete orphan and Received recovery never send again, descriptor/local-write restoration recovers without irreversible rejection, settled cache loss cannot fake old completion, changed canonical receipt cannot confirm staged refs, and same-ID policy changes cannot mix query/render configurations. Streaming source structure is not a measured RSS or latency benchmark. No live-provider, other-platform durability or power-loss claim follows from this review.

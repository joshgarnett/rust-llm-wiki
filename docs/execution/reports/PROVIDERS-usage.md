# Gateway usage compatibility and accounting

This leaf change recognizes the gateway's embedding, Chat Completions, and Responses usage shapes without relaxing the paid-observation boundary. Embedding `completion_tokens: 0` and null detail objects are valid; nonzero embedding completion remains unsupported. Chat and Responses use distinct field names but the same input/cached and output/reasoning partitions. Missing cached or reasoning counts remain Unknown.

The shared parser validates recognized nonnegative counts, checked totals, subset bounds, cache-read and cache-creation alias agreement, and disjoint cached/write and reasoning/text partitions. Informational text-token counts are not charged twice. Explicit zero cache creation/write annotations are harmless. Positive creation/write annotations make cost Unknown for compatible deployments; with an exact documented basis they trigger the existing `UnexpectedBillableClass` stop. Unknown bounded usage extensions permit output decode but make computed cost Unknown. An untrusted `usage.cost` value never supplies settlement authority. Actual usage remains attached to incomplete or invalid output.

`wire_json::usage_valid_for(p,v,generation)` selects Responses field names from the sealed `GenerationContract.surface`; the existing `usage_valid(v,generation)` remains the Chat/embedding compatibility entry point. `supported_usage`, `totals_within_contract`, and `observe` use the same surface-aware analysis. The generation worker must call `usage_valid_for` for Responses decode.

Nested tests in `src/providers/wire_json.rs` cover the supplied embedding, Claude/GPT Chat and GPT/Claude Responses usage samples, zero/null annotations, unknown and positive creation extensions, exact-basis classification, malformed counts, aliases, overlap, overflow, duplicate JSON keys, and missing partitions. Worker ran `rustfmt` only; root owns all Cargo/Bazel execution and integrated results. No live provider or paid request was used.

`tests/remote_cli.rs` adds native loopback `doctor --probe --role generate` cases: Responses requests use the default 256 output tokens or a configured service cap of 64, Chat retains its `max_completion_tokens` field with default 256, and an incomplete Responses reply yields the fixed reason in both the CLI error and one retained paid usage receipt. A caller `--max-output-units` ceiling against an unknown gateway must fail before transport because the gateway has no proven token upper bound. Each mock server has a finite accept/read deadline; the preflight rejection has no server thread.

## Findings

### G1 — P2: source-filtered graph/context results emit other sources' evidence

`--source-id` is described by the CLI as a filter applied before result limits (`src/cli/arguments.rs:364`). The candidate SQL accepts an assertion when *any* associated evidence has the selected source ID (`src/retrieval/filters.rs:85-92`). Graph evidence expansion then iterates **all** evidence for that assertion without applying `plan.filters.source_ids` (`src/graph/traverse.rs:200-229`), and context repeats that behavior in `bundles::select` (`src/retrieval/bundles.rs:292-321`). Context rechecks filters on assertion/path documents only (`src/retrieval/context.rs:430-464`). Thus the filter scopes candidate assertions, but not returned evidence or source bytes. This distinction is not disclosed in the output.

Reproduction on the disposable P21 fixture: `lwiki --wiki /private/tmp/lwiki-audit-graph-dAXyAR --offline --json graph query uses --strategy relationship --source-id source_00000000-0000-7000-8000-000000000005` returns support from sources `...005` and `...006`. The corresponding `context uses --target graph --strategy relationship --source-id ...005 --verification-max-elapsed-ms 30000` returns a verified current passage/citation whose `reference.source_id` is `...006`. The executable check at `/private/tmp/lwiki-audit-graph-dAXyAR/repro_source_filter.py` asserts this for both commands. The fixture's forward assertion has active support from both sources. A caller using the source filter to restrict what enters a context or agent prompt receives out-of-scope source content. This is a scope/contract mismatch, not evidence-integrity failure: the other-source citation itself is valid. Either enforce source scope on emitted evidence (and disclose omitted counterevidence), or expose a separate explicit “candidate source” filter and make the all-evidence expansion clear. Confidence: high for behavior and reproduction; medium for desired policy because the technical contract does not define whether source filtering is intended to restrict candidate assertions or every emitted passage.

### G2 — P2: semantic candidate cap applies to units before owner collapse

The exact scan keeps only `k` highest-scoring **units** per target (`src/retrieval/vectors.rs:575-616`). The document search groups those already-capped hits by owner afterward (`src/app/embeddings.rs:1297-1304`, `src/retrieval/fusion.rs:15-34`). With default `k=80`, one long document whose 80 units outrank the best unit of every other document leaves only that one document in the dense candidate list. The next best document is absent before RRF, even when there is room for 79 more document hits. The contract says to collapse document units by owner before fusion, retaining their best rank and up to two passages (`docs/technical/retrieval.md`, “Graph candidates, fusion, and budgets”). The application also discards the collapse function's second passage as `_passages` (`src/app/embeddings.rs:1304`), so that passage cannot be surfaced as a second context candidate.

Packaged-binary reproduction: `/private/tmp/lwiki-audit-graph-dAXyAR/repro_semantic.py` creates a fresh two-page vault and serves only a loopback mock embedding API. The long page yielded 225 distinct units scored at cosine 1 against the query; the other page yielded one unit scored at cosine 0.8. The sync generated all 226 inputs; query output reported `semantic coverage 226/226 eligible units; 0 missing, 0 corrupt`, yet `candidate_count=1` and only `knowledge/pages/long.md` was returned. The disposable output vault is `/private/tmp/lwiki-semantic-audit-jvf7yi0w`; the mock handled 16 local HTTP requests and made no external request. A regression should cap distinct owners while retaining the best two unit spans for each, then confirm both documents survive and only one owner vote enters fusion. This is a retrieval-quality defect under the present bounded top-unit heuristic; the design's wording does not unambiguously require a top-*owner* cap before the per-target heap. It is independent of the reported B12 6-unit case and does not measure live-provider quality. Impact: lost semantic recall and underfilled result/context budgets for segmented corpora. Confidence: high.

### G3 — P2: `context --navigation` drops all navigation edges silently

The context CLI accepts and forwards `--navigation` (`src/cli/context.rs:46-48,112`), and graph traversal produces a separately labeled `GraphResult.navigation` stream (`src/graph/traverse.rs:595-701`). Context assembly validates the combined assertion/navigation count (`src/retrieval/context.rs:378-382`) but loops only through `graph.assertions` (`src/retrieval/context.rs:427-485`); no navigation packet, rendered edge, or omission is produced. The contract explicitly includes requested page-link expansion and says navigation consumes the same budgets (`docs/technical/retrieval.md`, “Graph candidates, fusion, and budgets”).

Reproduction: in the copied P21 fixture, append `[[south_lab.md]]` to the `north_lab.md` entity body. `graph query 'North Lab' --strategy entity --navigation` then returns one navigation edge; `context 'North Lab' --target graph --strategy entity --navigation --verification-max-elapsed-ms 30000` returns no navigation information or navigation omission (while returning assertion bundles). For a navigation-only result, the context text can be empty and `truncated=false`. Pack bounded, distinctly labeled navigation records under the existing context budget, or explicitly reject this unsupported flag on context. Confidence: high.

## Cross-module follow-up: storage S2 reaches API dispatch and catalog reads

**High severity; high confidence.** The storage audit's S2 malformed duplicate source ID is more than an inaccurate `ready_to_import` flag. `SourceView::resolve` counts only parsed `note.fields` (`src/sources/revision.rs:220-250`), while the canonical catalog reserves a readable ID from an otherwise malformed note and excludes both duplicate records (`src/catalog/scan.rs:138`, `docs/technical/storage.md:51,135`). The reused packet therefore passes extraction planning (`src/app/extraction.rs:94-140`) and the same weaker source/packet checks after API dispatch (`src/graph/api_extract.rs:336-363`). `catalog.guard_current(None)` guards unresolved change journals, but does not require the packet's source to remain in the canonical registry. After a valid generation response, the generation-output catalog projection unconditionally calls `expect("valid packet source")` on the absent source (`src/catalog/eligibility.rs:825-865`). The design calls for malformed/duplicate metadata to exclude typed resolution and become diagnostics, while newly introduced duplicate identities must be detected before verified output (`docs/technical/storage.md:51,137-141`); neither an API request nor a process panic is an appropriate diagnostic for this state.

Two packaged-0.1.2 reproductions isolate the consequences. First, `/private/tmp/lwiki-audit-graph-dAXyAR/repro_s2_api.py` copies the storage audit's `reused-duplicate` vault, verifies `graph extract --executor agent` returns `persisted=true`, `ready_to_import=true`, `reused=true`, and runs `graph extract --executor api` against a loopback-only chat-completions mock returning a syntactically valid empty extraction. The mock received **one** HTTP generation request. The CLI then exited 101 with the `valid packet source` panic, no JSON envelope (`/private/tmp/lwiki-s2-api-iadmx46f/result.json`). The raw response spool and run genesis survive, but no canonical generation output or receipt was present in that reproduction. This establishes a request that could incur a provider charge before canonical refusal; it does not by itself establish final ledger accounting behavior.

Second, `/private/tmp/lwiki-audit-graph-dAXyAR/repro_s2_clean.py` starts from a *valid* copied bootstrap vault, exports its packet, and completes one mocked API extraction, retaining a generation output (`/private/tmp/lwiki-s2-clean-w8rku3az/vault/runs/run_s2_clean/outputs/`). Adding the same malformed duplicate source note afterward makes ordinary offline `check`, `index sync`, literal `search`, and `graph query` each exit 101 at `src/catalog/eligibility.rs:865`, without a JSON error. In contrast, those commands on the first vault, whose failed API attempt left no canonical output, did not panic: `check` diagnosed the malformed duplicate and invalid references. Thus the retained output plus subsequent identity invalidation can prevent catalog projection and ordinary reads until the malformed note is repaired. `docs/technical/retrieval.md:26` explicitly keeps invalid notes searchable as lexical locators, so a malformed note should not crash retrieval.

I also submitted the same valid empty response to `graph import` in the already-ambiguous vault. Import returned a prepared extraction change, but `changes apply change_01a0ef7d-e371-7d21-968c-d2f2f01cfb9f` rejected it with `RECORD_INVALID` for the proposed extraction note. Its `wiki_source_ids` require canonical typed references (`src/graph/import.rs:46-100`, `src/catalog/eligibility.rs:445-555`). No invalid extraction, assertion, or accepted fact was published in these checks; the model response contained no assertions, so this is not a complete proof for every possible response. Resolution operates on canonical extraction records and does not make the staged one authoritative. The immediate repair is to share canonical identity reservation with `SourceView`, validate current typed membership before API dispatch, and replace the generation-output `expect` with an invalid/unsupported diagnostic. Add regressions for both an ambiguous source *before* dispatch and a previously retained output whose source later becomes ambiguous. These follow-up checks used only disposable fixture copies and a local mock; they did not contact or qualify a real provider.

## Live-0.1.2 report follow-up: quotation repair and withdrawn-source discovery

### G4 — P2: quotation rejection omits the information needed to repair paid extraction output

The live-host report says API extraction succeeded for one of six `webtext` sources and the other five returned `EXTRACTION_INVALID: quotation must have one exact match in its declared window`; ASCII-only material also failed. I did not access the host, its providers, or those five responses, so the failure rate and specific model quotations remain reported observations. The local validator explains why the error is uninformative: for an omitted span, `unique_quote_span` returns the *same* text when a quote has zero matches or multiple matches (`src/sources/evidence.rs:16-46`). `wire::trace` passes that error through without mention ID, assertion/evidence index, window ID, match count, or matching byte offsets (`src/graph/wire.rs:62-83,127-142,172-179`). The API adds run/task/packet and coverage to the error, but `retained_details` remains null for this case (`src/graph/api_extract.rs:612-621`). Its generation path validates the whole response and rejects it before import if any item fails (`src/graph/api_extract.rs:352-382`). This strict atomic check is required for traceability (`docs/technical/storage.md:61`, `docs/technical/retrieval.md:118-122`); accepting unmatched facts would be a regression.

The packet's fixed instruction says to “quote exact source bytes” but does not say that a quote without an explicit span must be unique within its window, or that `span` is an absolute **UTF-8 byte** range (`src/graph/packet.rs:21`; the contract spells this out at `docs/technical/retrieval.md:120`). `/private/tmp/lwiki-audit-graph-dAXyAR/repro_quote_diagnostic.py` copies the bootstrap fixture, exports a packet, and imports three ASCII-quote responses with the packaged 0.1.2 binary. `Lab` occurs six times in window `w1`; an absent ASCII phrase occurs zero times. Both exit 9 with identical `EXTRACTION_INVALID` message and null details. Adding the exact absolute byte span to the repeated `Lab` mention succeeds and returns a prepared import (`/private/tmp/lwiki-quote-audit-j6fza9u4/result.json`). This establishes ambiguity with an ASCII quote, independent of curly-quote normalization, and a valid local repair path; it does not show what caused each live-host failure. Improve item-level diagnostics (local ID or array index, window ID, zero-versus-multiple match count, bounded candidate byte spans or a safe quote fingerprint) and teach packet instructions the uniqueness/span rule. Given access to the original model JSON, a host can correct only the failing quote/span and resubmit it through `graph import` without another model call. Retaining/recovering rejected paid output and its accounting is a separate provider-ledger question; no automatic paid repair or acceptance of unsupported facts is implied.

### G5 — P2 policy inconsistency: default search exposes current-labeled decision prose after source withdrawal

Review decisions deliberately persist editorial rationale and must remain authoritative for review/identity history (`docs/knowledge-graph.md:13,68`; `docs/technical/record-schemas.md:29`). Their eligibility changes only on decision supersession, not when evidence loses source support (`src/catalog/eligibility.rs:911-913`), which is appropriate for the *decision record*. However, catalog projection includes the review body as ordinary indexed Markdown because the exclusion set omits decisions (`src/catalog/scan.rs:303-315`). Default search permits any `current` document and does not exclude decisions (`src/retrieval/filters.rs:101-132`), so source-derived words copied into rationale or its retained request can appear in ordinary search as `eligibility=current`, with `label=note_text` and no citation. This differs from the current-context policy, which admits source payloads and reviewed pages/current entity descriptions, but not decisions (`src/retrieval/filters.rs:138-156`). The design requires withdrawal to remove active support and prevent withdrawn/unsupported current-evidence leakage, while preserving historical access and decisions (`docs/knowledge-graph.md:95-97`, `docs/technical/retrieval.md:134,148`). It does not explicitly settle whether an audit decision's author prose should remain discoverable by default.

Packaged-binary reproduction `/private/tmp/lwiki-audit-graph-dAXyAR/repro_decision_search.py` copies bootstrap, creates and applies a valid review of the singly supported negated assertion with rationale `North Lab does not use South Lab.`, then withdraws its sole supporting source. `check` remains clean. Default literal search for that full phrase returns only `knowledge/decisions/decision_01a0ef85-4a19-7360-9a24-a51181919398.md`, `kind=decision`, `eligibility=current`, with the rationale in the excerpt; default lexical search also includes the decision. The exact assertion-kind search yields no hit, and verified `context --target documents --mode literal` yields no passage or bundle. Logs are at `/private/tmp/lwiki-decision-audit-yf5zo9qh/result.json`; the context and lexical follow-up were also checked directly on that disposable vault. This is **not** an accepted-fact, citation, graph, or current-context leak. It is a misleading current-search discovery path for audit prose that may quote withdrawn material, matching the user's live report's decision-path symptom. Define an explicit audit/historical retrieval scope for decision bodies or exclude bookkeeping decision bodies from ordinary text candidates while retaining their canonical decision effects and direct reading. If decision discovery remains default, label it explicitly as editorial/audit text rather than current evidence and prevent it from occupying source-evidence search budgets. Do not invalidate merge, alias, or review authority merely because a cited source was withdrawn.

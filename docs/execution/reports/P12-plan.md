# P12 bounded interface proposal

This document proposes a root-owned freeze; it does not register capabilities or claim readiness. Worker lease is this report and `/tmp/lwiki-p12-types-proposal.rs` only. P11 defects take priority.

## Minimal request and APIs

Strict `lwiki.entity-decisions.v1` has `decisions` (1..16; total wire256KiB). Each internally tagged PascalCase arm owns its fields and rejects unknown/duplicate/null values:

- `MergeEntities`: `reason`, `expected_records`, `remaps`, `source_ids`, `target_id`.
- `SplitEntity`: `reason`, `expected_records`, `remaps`, `source_id`, `new_entities:[{key,title,entity_type}]`.
- `AddAlias`: `reason`, `expected_records`, empty `remaps`, `entity_id`, `alias`.

Remaps are a strict tagged union of assertion field (`subject_id|object_id`, assertion ID) and extraction/local mention (extraction ID, mention ID), each with old entity and exactly one target: existing entity ID or split-local new-entity key. Keys are scoped to their split operation; a model/local label cannot become a global ID. Each expected record has canonical ID/hash; normalized order is unique by ID. Reject duplicate references, overlapping operation scopes and cross-operation key references. Normalize independent decisions by canonical JSON bytes, then assign deterministic ordinals; caller list order has no execution semantics. Request hash includes every effective field.

Proposed ceilings: reason4096bytes, title1024, alias1024, registry entity type, each merge1..16 absorbed sources, split2..16 new entities, JSONdepth32/nodes65536, all remaps1024, all expected records4096, receipt2MiB, total generated operations/read guards≤existing ChangeEngine10,000. Complete bounded canonical capture uses existing64MiB/4096-document limits. Reject before cloning/allocation when any bound is exceeded. These are safe refusal bounds, not an exemption from exhaustive validation. Root must freeze them before code/schema.

Leaf APIs mirror P11: `validate_entity_decisions(view,bytes)->ValidatedEntityDecisions`; `plan_entity_decisions(validated)->EntityDecisionPlan`; `stage_entity_decisions(engine,writer,validated)->EntityDecisionOutcome`; `load_entity_decision_receipt(view,task_id)->Option<VerifiedEntityDecisionReceipt>`. Validated/verified wrappers are sealed, with read-only getters. Pure validation/planning allocate no IDs. Stage always prepares a guarded changeset; the app decides normal apply versus staging. Proposed new origin `GraphDecide`, task scope `entity_decisions_<hash(normalized guard/scope descriptor)>`, response hash normalized full request. Same guarded scope/different request conflicts; later hashes permit a new explicitly authorized operation.

## Exhaustive reference and mutation proof

Proposal defines merge `source_ids` as **absorbed IDs excluding the retained active target**; target is separately hashed. Split supersedes its one active source and allocates distinct new identities. Every canonical assertion subject/object reference to an absorbed/split source, including historical assertions and each distinct field, and every Resolved extraction mention to that source must appear exactly once. Pending/Rejected proposals have no inferred endpoint and receive no remap. Equal names/aliases/types never resolve a partition. Materialized extraction propositions and their corresponding mention remaps must agree; reserved assertion/evidence IDs remain fixed. Empty partitions may create an explicitly requested new identity but never infer a reference assignment; all existing references still require exactly one target.

Hash all affected entities, assertions, extraction envelopes and predecessor decision notes; preserve complete source/raw/span/allocation proofs and capture their bounded physical dependencies. Capture every canonical document as an observed guard where used to establish completeness. Description support keeps its assertion IDs and is reprojected, never treated as authorization for an endpoint change. No synthetic closed missing-asset states become physical reads.

An apply/recovery validator must re-enumerate the **whole current canonical reference set**. Existing-file guards alone miss a new referring note. During partial forward recovery, reference membership combines still-old endpoints with exact already-applied declared remaps, verified against retained old/new payload hashes; an unfamiliar old reference or third-state target conflicts. Publication repeats the policy. Root must implement this boundary in the real validator, not a preparation-only partial view. Fresh canonical rebuild verifies that active receipts and current remaps agree, without replaying old bytes.

Root currently prohibits every assertion proposition change. Add a **sealed exact-overlay authorization** constructed only after strict receipt/request validation against the actual bounded before/proposed graph. It authorizes only listed subject/object differences, with exact old/new IDs, identical predicate/literal/property/negation/modality/unit/interval, unchanged evidence/source trace, complete hash/reference membership, and matching explicit canonical decisions. Ordinary edits, fabricated proof tokens, hidden companion changes and redirect traversal remain forbidden. Proposal resets remapped accepted assertions to proposed, retains rejected/superseded status, and never authorizes acceptance; root must freeze this status choice. Reassessment belongs to P13.

## Mention successors and conflict policy

Each remapped Resolved mention receives a new explicit active `bind_mention` decision. Its `wiki_supersedes_id` names the old Bind/Create decision; the old decision becomes superseded in the same changeset, and the complete artifact binding points to the new entity/new decision. Rationale and a strict receipt identify the governing main Merge/Split decision. Original raw response, source windows/spans, reserved maps and materialized-ID set remain immutable. AddAlias records explicit alias addition and empty remaps; it does not supersede mention authority or bind anything.

One predecessor may cover several mentions while `wiki_supersedes_id` is singular. Such a predecessor must have **all of its mention authority replaced together**, with every affected extraction hashed and each mention explicitly represented, including an unchanged entity assignment needed to retain the predecessor's other authority. Otherwise refuse; never mark a decision superseded while leaving current bindings pointing at it. Multiple successor decisions may name one predecessor, one per mention; each has a distinct scope. The request remap format must support these explicit carry-forward mappings without treating them as endpoint changes.

Main merge input IDs are absorbed entities; output is retained target. Split input is old source; outputs are new entities. Split source is superseded without inventing a single redirect destination. Root Catalog compatibility must recognize the main decision plus its exact receipt-bound scoped replacements, including historical main decisions affected by subsequent authorized operations. Only this verified family may overlap affected identities; arbitrary active merge/split/global decisions still conflict. Existing alias, global review, supersession-cycle and distinct-mention invariants remain enforced.

For sequential merge/split operations, enumerate every active prior main decision whose outcome would cease to hold (for example, its retained output is now split/absorbed). The request must hash each such prior decision; mark it superseded in the same changeset and retain exact predecessor→new main edges in the new strict receipt. If there is one predecessor, also use the ordinary `wiki_supersedes_id`/companion; with several predecessors omit that singular field and use the receipt's complete explicit edge set, which root Catalog must validate and include in cycle checks. This avoids adding an overloaded/list frontmatter field or allocating synthetic decisions. An earlier main decision whose outcome remains true may remain active: two merges retaining the same target may commute only when strict receipts prove distinct absorbed scopes and consistent current outcomes. An earlier main decision covering unaffected branches is historical once any outcome changes; all still-current mention authorities remain explicit independently. Arbitrary review/correct/reject conflicts are not silently superseded or reclassified.

## Receipt and historical acknowledgement

Freeze `lwiki.entity-decision-receipt.v1`, actual unique fence `lwiki-entity-decisions-v1`. Receipt contains normalized request/task/hash, allocated main/entity/replacement IDs, exact original record paths, complete affected prior artifact maps/materialization lists and immutable artifact hashes, exact assertion endpoint transitions plus invariant-proposition hashes, predecessor/successor/main decision relationships (including complete main supersession edges), and sorted before/after operation proofs. Record path keys are exactly proof-participating IDs. Receipt copies in the new decision notes exclude **all decision-note hashes** from operations to avoid recursive hashes; actual retained manifest remains authority for every decision payload and before-image. Decision-note status/supersession changes instead have strict semantic proof fields tied to hashed expected records. No lost manifest or historical whole-note bytes are invented.

P10/P11 restoration needs a shared sealed `verify_authorized_binding_evolution`/`verify_authorized_proposition_evolution` boundary. It must follow an explicit bounded successor chain (proposal maximum64 hops), prove every predecessor/successor edge and main exact remap receipt, reject forks with contradictory current scope/cycles/missing links, resolve current stable IDs independently of saved original paths, and preserve original resolution/reserved IDs. This is distinct from fresh P11 Pending-only transition permission. Original resolution acknowledgement after remap proves the original semantic request and the explicit subsequent chain; it never reapplies the original endpoint/author bytes. Later reviewer statuses, evidence successors/retractions and entity/extraction path/title/prose edits remain permitted where identity/proofs are preserved. Before chains exist, P11 continues to fail closed on remaps.

Search retained and canonical receipts before ID allocation. Allocate split entities/main decisions/replacement decisions only inside `prepare_or_reuse.build_once`. Identical retained outcomes preserve honest statuses; canonical-only acknowledgement preserves IDs and returns no invented PreparedChange/status. Pair retained and canonical immutable IDs/maps/proofs exactly, allowing only separately verified authorized evolution. Source/model output cannot invoke decisions.

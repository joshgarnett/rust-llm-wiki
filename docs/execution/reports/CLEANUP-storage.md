## Observed constraints

- `changes/recover.rs` correctly refuses durable Conflict, but the journal has no outgoing resolution transition. Simply allowing Applying from Conflict loses the distinction between a proposal with no trustworthy intent and an interrupted owned immutable revision tree.
- `changes/apply.rs::retain_validation` binds a full projected canonical scan. Restoring target hashes alone does not resolve a conflict caused by a changed read dependency or unrelated canonical document. Original `validation.json` also anchors `revision-trees.json`; replacing it invalidates immutable ownership.
- `changes/prepare.rs::load_manifest_with_budget` calls `validate_manifest`, which reads **every before/proposed payload** and infers roles/dependencies from the bytes. Even ordinary terminal inspection currently depends on all retained payloads. Fixing only jobs' checkpoint lookup does not make changesets prunable.
- `jobs/checkpoint.rs::verify_summary_proof` reconstructs an obsolete run note by scanning committed changes and reading a matching proposed payload. `ledger.rs::load` does this for every historical checkpoint. Checkpoint acknowledgment additionally requires every event Markdown mirror. Receipt recovery searches committed manifests, while inverse/decision ancestry uses retained graph operations.
- Operational job history is capped at 64 MiB/65,536 events and carries exact admission, send, response, reconciliation, settlement, and task transitions. Its permanent unknown-charge holds cannot be replaced by aggregate spend counters. Existing spool removal checks settlement/receipt/output hashes, but historical proof and diagnostic retention still need an explicit policy.

## C01: smallest compatible resolution

Expose a read-only `resolution_plan(change)` and writer-locked `resolve(change, plan_digest, mode, validator, publisher)`. CLI can present `changes resolve ID --mode resume|abandon --dry-run`, requiring the expected manifest and plan binding for mutation. The plan includes vault/change/manifest identity, current conflict frame sequence and hash, sorted complete observations (including absence), original read guards, immutable ownership status, and resolution restrictions. A fresh CLI invocation can calculate and consume the plan under its held lock; a caller-supplied digest additionally guards a prior review. No ordinary apply/recover route gains Conflict authority.

A new explicit journal event such as `ResolutionAccepted { conflict_sequence, conflict_frame_hash, mode, observations, validation_hash }` must be legal only after Conflict, verify the cited immediately preceding conflict and full target coverage, and begin a new resolution epoch. Terminal receipts retain this event. The API must validate hashes/guards **before** recording authority; the journal decoder also rejects structurally invalid resolutions. Repeated invocation after an interrupted accepted resolution continues the same epoch; a new third hash produces another durable Conflict. Do not invent a success receipt just because files happen to match.

**Resume:** all targets must be exact before or proposed states; any unfamiliar bytes stay untouched. Recheck original read conditions, retained payload integrity, original immutable tree ownership, complete tree membership, competing owners, other unresolved changes, and proposed graph. Resume then uses normal per-operation intent/done and final publication checks. A lost operational journal plus matching revision bytes cannot establish ownership: existing original ownership receipt and validation baseline remain required. If no immutable target exists yet, ordinary absent-tree preflight can establish ownership before application.

The narrow first slice may require the original retained validation scan to match. It must diagnose why an otherwise reconciled target still fails. To allow unrelated benign edits, retain a **new immutable validation receipt per resolution epoch**, journal-bind its hash, and use it for resumed projected-scan comparison. Preserve original `validation.json` unchanged for revision ownership. Changed original `read_preconditions` still prohibit resuming the old proposal: fresh validation cannot silently rebind source evidence or target expectations.

**Abandon:** the smallest safe route is reconciliation without engine target writes: require every target, including immutable assets, to equal its original before state and validate the actual current graph, then record explicit resolution and terminal Aborted. For a mutable-only partially applied change, a bounded guarded restore can additionally reverse only exact proposed states in reverse dependency order, retaining normal per-operation intent/done; every third hash is preserved. This is a real resolution state machine, not a temporary exemption for unrelated writes. Validate the restored graph before declaring terminal, and ensure readers cannot reuse a previously published projected snapshot as current.

A partially created immutable revision cannot be deleted or simply disowned by generic abandonment. Support completion using the retained ownership proof, followed by an ordinary guarded inverse/withdrawal as appropriate; source-add inverses already refuse orphaning revision trees. If full direct abandonment of such changes is required, design a separately recorded reconciliation that completes and retains the immutable tree and repairs its owning source under explicit validated operations. Do not call this ordinary Aborted. The first guarded route is useful but this limitation must remain explicit rather than claiming every conflict is recoverable.

**Counterexamples to shortcuts:** Conflict→Prepared makes a previously applying mixed operation appear unapplied; Conflict→Applying can claim independently created identical revision files; replacing validation loses the ownership baseline; Aborted with a live newly created revision removes its competing-owner protection; bypassing the vault guard for rollback publishes while another unresolved target remains. All are rejected.

## S01 inventory and lifetime classes

Report file count, logical bytes, global unique content bytes (BLAKE3+length), duplicate bytes, and optionally filesystem allocated bytes with a clearly separate name. Record per-operation before/after deltas and cumulative bytes written, because retained size alone does not measure write amplification. Global unique totals cannot be obtained by summing independently deduplicated class totals. Never equate duplicate bytes with reclaimable bytes.

| Class | Examples | Default protection |
|---|---|---|
| Readable knowledge | pages, entities, assertions, decisions, reports | Retain; ordinary current discovery applies lifecycle filters |
| Evidence/provenance | source manifests/revisions/originals/normalized text, evidence, accepted extraction provenance | Retain referenced history; no deletion solely by age |
| Active work | pending packets, unresolved changes, unfinished provider responses | Protect until explicit supported terminal transition |
| Recovery/accounting | manifests/outcomes/ownership, job journals, usage receipts, replay identities, proof objects | Retain necessary authority; compact only with verified replacement |
| Optional diagnostics | rejected raw model text, HTTP diagnostic bodies, debug material | Bounded age/bytes policy after terminal disposition and accounting protection |
| Rebuildable cache | SQLite projections, vectors, scan cache | Reclaim separately; vector loss may require explicit paid work to restore |

Inventory must enumerate bounded contained regular files, refuse symlink traversal, account unknown files as protected/unclassified, and expose incomplete-scan status rather than return exact-looking totals. Pure inventory/preview must not initialize cache, checkpoints, or journals. Initial preview should say `protected: unsupported_retention_migration` for history currently required by the code, not speculate that old terminal changes are safe to delete.

## S02 layout without breaking portable references

Introduce a versioned internal layout resolver, e.g. `.wiki/retained/{changes,objects,jobs,packets,proofs,diagnostics}` alongside existing durable `.wiki/state` and replaceable `.wiki/cache`. It is inspectable local data, required in full backups, never implied disposable by its hidden path. Keep visible source/evidence/knowledge pages and concise human run reports. Operational detail commands provide the full history.

Initial adoption can put **new** transaction storage and objects inside this resolver while accepting legacy `changes/` and `runs/` locations. Do not relocate existing packets/receipts through raw filesystem renames: exact path/hash references occur in immutable manifests, run events, packet payloads and graph receipts. Existing and internal packets still require deterministic typed identity discovery/validation, but should not automatically supply ordinary knowledge search text. Separate typed canonical discovery from human/semantic search eligibility; `.wiki` currently skipped by general scans is not sufficient.

Migration uses a retained checksummed manifest binding vault/layout versions and exact old logical path/hash to new immutable location/hash, with collision/ambiguity refusal. Legacy logical references continue resolving through an explicit narrow storage resolver, not an unbounded path alias mechanism. Never rewrite historic source bytes, quotations, packet hashes or checksummed transaction manifests. A backup containing only visible Markdown is documented as knowledge-only and cannot claim resumable accounting or replay restoration.

## S03 compact proofs and lower writes

The practical first implementation keeps one immutable operational event stream; it does **not** discard event history or introduce an unproven snapshot replay engine. Remove new one-Markdown-per-event mirrors after adding a new checkpoint proof version. A compact checkpoint proof binds:

```
version, vault_id, run_id, spec_hash, genesis_hash,
through_event {sequence, event_id, checksum}, formatter_version,
run_note {record identity, logical path, exact byte hash},
completed_task_summary {count, digest}, committed_change {id, manifest_hash}
```

Retain it in a checksummed Markdown proof envelope, with the corresponding commit evidence. It is a reference to evidence, not self-authenticating merely because it is checksummed. Verification replays the exact retained event prefix, regenerates v1/v2 run bytes using the pinned serializer, checks the exact hash and completed-key summary, and verifies that the retained committed change binds the same output. This removes dependency on old `run.md` **payload copies** without losing exact-byte proof. Keep old formatter code while old proofs exist. Prefix verification must not require a current output to equal every historical version.

Split changeset APIs into `inspect_history` (strict manifest structure/hash plus retained terminal transcript) and `load_for_apply_or_inverse` (full byte/role/dependency validation). Add a narrowly sealed `CommittedOutputProof` returned only after engine verification, binding original exact manifest bytes/hash, terminal transcript, and selected operation target/after hash/identity. Preserve original manifest and terminal receipt, which are compact relative to copied run payloads. A missing before-image then yields an explicit unavailable-undo result for pruned changes, while terminal history can remain valid. Never let historical inspection authorize fresh mutations or relax unresolved payload validation. Preserve graph decision/inverse ancestry payloads until a separate complete proof replacement exists.

Use content-addressed immutable blobs for transaction before/proposed bytes: `.wiki/retained/objects/blake3/<prefix>/<digest>`. Objects are written temp→fsync→rename→directory fsync, checked by length/hash on every authority-bearing read, and never exposed through writable hardlinks to user Markdown. Canonical files remain independent copies. New manifest v2 can use typed object references. Legacy manifests remain byte-identical; migration records can map their exact original payload reference plus manifest hash/op/side to verified objects. Do not silently reinterpret arbitrary v1 paths. Equal before/after snapshots across transactions reuse one object; shared immutable source copies can be evaluated later without rewriting source format.

Avoid repeatedly checkpointing merely to mirror the previous checkpoint event: checkpoint work should compare substantive state, and an identical state should allocate no new change. Coalesce run-summary writes at existing safe boundaries, while each admission/dispatch/response/settlement event remains durably ordered in the single journal. Retain compact immutable per-attempt usage receipts and accepted output identities. A provider response body can be dropped only after materialization/rejection is durable and diagnostic policy permits; its usage/unknown-charge authority cannot be dropped with it.

This cuts three concrete multipliers: Markdown event mirrors, transaction copies of those mirrors, and repeated run-state payload versions. Retaining one event journal remains intentionally linear in real work, not zero growth. Later segmented immutable journals are possible, but retaining original events avoids a much larger accounting replay redesign now.

## S04 explicit migration, retention and GC

1. Add dual readers/layout resolution and compact proof readers first; keep v1 behavior available. Add historical inspection without changing apply/inverse checks.
2. Under vault writer authority and properly ordered run locks, verify original manifests, journals, checkpoints, receipts and all authority edges. Produce migration plan with before hashes, protected roots, object mappings and expected reclaimable files. Dry-run is read-only.
3. Write/sync replacement objects/proofs first. Retain a migration manifest and durable activation record only after validating the new proof graph. Reopen via new readers and check identical accounting/task/replay/terminal outcomes. Existing history is not deleted at this step.
4. Recompute reachability for explicit cleanup with policy (bounded undo count/age/bytes and diagnostics age/bytes), retain the exact plan and mark it active, then delete only listed exact-hash unreferenced files with directory sync. Crash before activation leaves extra objects; crash after activation leaves extra old files. Resume/repeat is idempotent. Unknown or changed candidates are skipped/refused, never erased. Recheck authority roots when a preview is later applied.
5. Keep immutable migration/retention receipts explaining which undo bytes deliberately expired. Legacy strict readers must reject the upgraded layout version rather than dispatch with incomplete authority. Downgrade requires restoring the pre-migration backup.

Roots include unresolved/staged changes; all required immutable revision ownership; active packets/handoffs; canonical citation and extraction provenance; origin→allocated-ID replay mappings; active jobs; every unknown-charge hold and its attempt/binding/usage history; retained receipts/checkpoint proofs; graph correction ancestry; and changes within the chosen undo window. Terminal is not equivalent to unreferenced. Keep **all source revision bytes** in initial cleanup, even if presently unreferenced; source purge is a separate explicit future policy.

Define lock ordering before implementing GC: it must not race a job append between reachability enumeration and unlink. Existing code acquires run locks during ledger operations and sometimes invokes changeset inspection; do not invent an opposite vault/run acquisition path that deadlocks. A bounded two-phase GC epoch with root revalidation, or a single documented universal lock order, must be shared by every mutating participant. Merely holding a vault lock does not prove all operational writers stopped.

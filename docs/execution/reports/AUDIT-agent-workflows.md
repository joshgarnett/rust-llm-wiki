# Agent handoff and skill audit (read-only)

Audited `63b2439` against the released 0.1.2 binary `.artifacts/012-macos/lwiki` (`lwiki 0.1.2`), with no production vault, credentials, or network calls. Scope: `docs/technical/research-handoffs.md`, `docs/technical/cli-and-skills.md`, `docs/agent-integration.md`, maintained `skills/llm-wiki` entrypoint/commands/workflows/examples, research packet/submission schemas, `src/research`, `src/cli/research.rs`, dispatch/skill export, relevant Rust integration tests, and current-facing stale research references. Root owns any edits to code, public schemas, and general docs.

## Findings

### A1 — P2: Direct report and status omit retained/current-evidence freshness

- **Evidence:** `src/research/engine.rs:443-473` returns bare status or `ResearchReport`; `src/cli/research.rs:129-136` serializes them and does not set freshness metadata; `src/cli/dispatch.rs:740-745` only forwards these values. `ResearchOutcome` from resume/import does have `data.freshness: retained` (`src/research/engine.rs:294-310`), but the direct report has no equivalent. The handoff contract says report-only results use `freshness: retained` (`docs/technical/research-handoffs.md:23`); the skill directs agents to use `research status` and `research report` (`skills/llm-wiki/references/workflows.md:25`).
- **Reproduction:** In a disposable vault on the 0.1.2 binary, `research run` → collect inline `Cedar is a tree.` → answer citing `p1` → `source withdraw` on the imported source → `research report RUN`. The report still returns its `unassessed` cited claim, with no `data.freshness`, while envelope `meta.freshness` is `null`; `research status RUN` says `completed` with `meta.freshness:null`. `research resume RUN` returns `data.freshness:retained`. This is historical retention, but an agent consuming the direct report cannot distinguish it from currently supported evidence from that response.
- **Impact/recommendation:** A host could carry a withdrawn or refreshed citation into a maintained page. Label direct report/status as retained history, expose current source lifecycle or require explicit revalidation before promotion, and test the direct commands after refresh/withdrawal. Preserve immutable reports. **Confidence: high** for output mismatch; downstream agent misuse is a risk, not an observed host result.

### A2 — P2 product/workflow gap: Maintained skill does not complete source-to-maintained-page synthesis

- **Evidence:** The executable research recipe (`skills/llm-wiki/references/examples.json:555-633`) uses an existing source, imports **zero** new sources, emits one cited answer, then reads its report. Its subsequent withdrawal (`:635-654`) is of the preexisting source, with no report-to-page step. `skills/llm-wiki/references/workflows.md:15,21-25` explains `page put` and research separately but never connects report citations to reviewed assertions, a guarded page update, source refresh/withdrawal repair, or a repeat ingest cycle. `tests/skill_export.rs:387-411` checks packet stage, `unassessed`, and report citation, but not those transitions. `src/app/offline.rs:476-530` supplies hash-guarded page writes; `docs/technical/record-schemas.md:3` and `docs/technical/storage.md:67` define `wiki_depends_on_ids` for assertions supporting derived pages. These primitives are present, but no maintained agent recipe exercises their composition. No periodic semantic lint or page synthesis workflow appears in the skill entrypoint/workflows or CLI registry.
- **Promise/impact:** The skill advertises “maintain a local Markdown wiki” (`skills/llm-wiki/SKILL.md:3`) and agent guidance asks to capture sources and draft supported pages (`docs/agent-integration.md:34-39`). The user’s desired ingest → synthesis → maintained topic/entity pages, filed query answers, and periodic consistency checks are not achieved by the demonstrated handoff. A report remains an operational artifact whose claims are `unassessed`; it does not automatically become maintained knowledge (`docs/technical/research-handoffs.md:9,52`).
- **Recommendation:** Add an explicit host-agent workflow and disposable recipe: ingest new material; inspect/cite; stage/review supported graph facts where appropriate; author or update several topic/entity pages with assertion dependencies and `--if-match`; rerun after source refresh/withdrawal and repair/deprecate stale synthesis; file a query answer as a guarded page only when requested; document a periodic semantic check performed by the host using existing search/context/check/graph primitives. Do not restore a built-in research runner. **Confidence: high** for missing maintained coverage; quality of actual hosts is untested.

### A3 — P3: Progress inspection is too sparse to resume from status alone

- **Evidence:** `src/research/engine.rs:443-455` status exposes run ID, coarse `awaiting_agent`/`completed`, generation/round, counters/import count and packet fingerprint. It omits stage, outstanding `follow_up`, current gaps, remaining source/byte budgets, packet warnings, and `next_command`, despite the CLI help saying “Read local handoff progress and remaining work” (`src/cli/research.rs:29-35`, generated `skills/llm-wiki/references/commands.md:2453-2500`) and workflow saying status reads “progress and gaps” (`skills/llm-wiki/references/workflows.md:25`). `resume` provides the packet, and `report` provides gaps after an answer, so no data is irretrievably lost.
- **Impact/recommendation:** Agents polling status must know to call resume/report, and status can say `awaiting_agent` for a stale packet because it does not verify passage freshness. Include stage/remaining budgets/gaps or an explicit next action and freshness state, or correct the help/skill to say status is only a summary and direct agents to resume. Test status before/after follow-up and source mutation. **Confidence: high** for field omission, medium for severity.

### A4 — P2 documentation drift: Current-facing plans still promise the removed executor

- **Evidence:** `docs/architecture.md:7,11,183,187,189` describes a future standalone research runner, automatic research apply, and bounded URL fetch. `docs/implementation-plan.md:21,24,70` promises M4 HTTP search/fetch/generation and asks whether to move standalone research earlier. `docs/technical/implementation-handoff.md:20,24,63` still lists the old planner/acquisition package. `docs/external-research-prompts.md:10,14` asks reviewers to design a later CLI-owned runner. Also, `docs/technical/cli-and-skills.md:3` says its command examples are not runnable yet, and `docs/agent-integration.md:3` says no skill has been installed or shipped, despite the 0.1.2 export and passing maintained recipe. The historical research pages are explicitly exploratory, and `README.md:54` warns some plans are historical, but these pages still read as current implementation direction and conflict with the user's explicit deletion with no legacy compatibility. Root is tracking additional stale references in `docs/technical/README.md` and `docs/qualification.md`.
- **Impact/recommendation:** Mark superseded plans conspicuously at the top or revise current-facing architecture/implementation/qualification guidance to point at `docs/technical/research-handoffs.md`; retain archival research with an unmistakable historical label. **Confidence: high**.

### A5 — P2 product/workflow gap: Host cannot stage coupled page maintenance through the CLI

- **Evidence:** `page put` accepts one page and one optional `--if-match` (`src/cli/arguments.rs:190-202`); its implementation builds a `ChangeDraft` with one `ExpectedWrite` (`src/app/offline.rs:476-530`). Public `changes` commands only inspect, apply, abort, and roll back an already prepared change (`src/cli/arguments.rs:273-297`); there is no prepare-many/compose command. The private change engine can handle grouped operations (`src/changes/types.rs:88`, `src/changes/prepare.rs:199-207`), as other internal operations do. The maintained research recipe writes no topic/index/log pages (`skills/llm-wiki/references/examples.json:555-633`).
- **Impact/recommendation:** An agent can make a guarded topic page and then another page, but cannot present a coupled topic/index/progress update for one review or guard all expected old hashes as one recoverable unit. This is a reference-inspired product gap, not a hard violation of the current v1 `page put` contract. Start with a host-agent recipe that inspects all target hashes, stages each page, checks the resulting whole-vault state, and documents partial-update recovery; add a bounded multi-page preparation API if the desired maintenance workflow needs one guarded, recoverable changeset. This would not make multiple filesystem replacements atomic. **Confidence: high** for CLI surface, medium for priority.

### A6 — P2: Human presentation hides warnings and bounded-read truncation

- **Evidence/reproduction:** `src/cli/dispatch.rs:279-280` sets `meta.partial` and `ReadOutcome.truncated`, but `present` prints only `data.body` for a successful human read (`:1083-1087`). `src/main.rs:102-117` prints freshness and warnings only for read/context, with no partial notice. In a disposable 0.1.2 vault with page body `Cedar is a tree.`, `lwiki --offline read --id page_human --max-bytes 5` exits 0, writes `Cedar` to stdout and only `Freshness: verified_snapshot ...` to stderr. The JSON form correctly has `meta.partial:true` and `data.truncated:true`. Other successful human commands use generic data-only presentation (`src/cli/dispatch.rs:1145-1148`), dropping envelope warnings. A disposable unsupported `.pdf` `source add` returned `citable:false`/`extraction_status:unsupported` in human data but an empty stderr; the JSON result included the actionable warning “Original bytes captured only… The content cannot be searched, embedded or cited. Supply extracted UTF-8 .txt/.md text when needed” (`src/cli/dispatch.rs:832-833`). `docs/technical/cli-and-skills.md:99-111` expects human output to prioritize readable content and unresolved issues.
- **Impact/recommendation:** A terminal user can treat a prefix as the full record or miss why a captured file is uncitable. Route all human warnings/partial notices consistently, including exact returned byte range/next offset for bounded reads; preserve body-only stdout for piping if desired. Test human read truncation and a warning-bearing source capture. **Confidence: high**.

### A7 — P3 ergonomics: A too-small UTF-8 read budget returns no forward progress

- **Evidence/reproduction:** Both current and cached read paths reduce an end offset to a UTF-8 boundary (`src/app/offline.rs:400-419`, `src/cli/dispatch.rs:941-968`) without rejecting a zero-byte nonterminal slice. With a page body starting `🦀` and `--max-bytes 1`, the 0.1.2 CLI exits 0 with `body:""`, `range:{start:0,end:0}`, `truncated:true`; asking `--start 0 --end 4 --max-bytes 1` repeats the same result. An agent using the returned end as the next start can loop indefinitely.
- **Recommendation:** The bound itself is honored; add an actionable budget error or warning giving the minimum next UTF-8 scalar width so a caller knows how to continue. Test current and `--no-sync` reads. **Confidence: high** for reproduced behavior, medium for practical frequency.

### A8 — P3: Invalid page input does not identify the required envelope

- **Evidence/reproduction:** `page put` intentionally requires an adopted page record (`src/app/offline.rs:488-493`; `docs/wiki-format.md:29-31`). On the 0.1.2 binary in a disposable vault, sending `# Cedar\nCedar is a tree.\n` to `page put --file -` exits 9 with `RECORD_INVALID`, message `page put requires a valid page envelope`, `hint:null`, and `details:null`. `schema record` **is available** (`src/cli/dispatch.rs:66-83,138-174`); its page variant requires `wiki_schema`, `wiki_id`, `wiki_kind`, `title`, and `wiki_status` (`schemas/record-v1.json:61-113`). The maintained skill contains a valid sample (`skills/llm-wiki/references/examples.json:459-469`), but the failed command does not point to it or identify a missing field. `docs/agent-integration.md:49` asks that errors be actionable.
- **Impact/recommendation:** A host given ordinary Markdown cannot recover from this response without already knowing the record contract. Keep strict page identity and status validation. Add a field-specific diagnostic or a hint to `lwiki schema record` plus a minimal page example in `page put --help`/skill workflow; an explicit page initializer could be considered if recurring authoring proves cumbersome. **Confidence: high** for output, medium for priority. This is a usability gap, not a requirement to accept bare Markdown as a managed page.

### A9 — P2: Retained research report Markdown is opaque in an Obsidian reading workflow

- **Evidence/reproduction:** `src/research/storage.rs:119-143` writes every research artifact as generic `# Agent research` followed by one `lwiki-agent-research-v1` JSON fence. A disposable 0.1.2 run with one cited claim and one gap produced `runs/run_n5/outputs/report_*.md` whose claim text, citation, question, and gap occur only inside a minified JSON fence; there is no ordinary prose summary or `[[...]]` link outside it. The JSON remains machine-readable and bound by the immutable artifact hash. `docs/wiki-format.md:64` expects completed run events to include a short explanation and enough readable metadata for recovery, and `README.md:7` describes Obsidian-compatible Markdown as canonical knowledge. `docs/technical/research-handoffs.md:15` explicitly chooses immutable RunEvent artifacts, so their path/layout is intentional.
- **Impact/recommendation:** A person browsing the vault cannot skim a retained research result, follow source links, or see unresolved gaps without opening/parsing JSON or using `research report`. This compounds A2's missing synthesis-to-pages workflow but is distinct: even the retained history is not readable as a research note. Render a bounded human-readable question, claims marked **unassessed**, source/revision wikilinks, gaps, and completion reason alongside the authoritative JSON fence for new artifacts; retain exact structured data and immutable hash semantics. Consider a separate derived Markdown view if changing canonical artifacts is undesirable. **Confidence: high** for file shape, medium for severity.

## Alignment and limits

- The implementation contains local packet, capture, citation, receipt, guarded publication, resume and report code in `src/research/{engine,storage,inspection,codec,types}.rs`; `src/cli/research.rs` has no built-in search/fetch/generation executor. The capability registry advertises `research_executor: agent-handoff` and only packet/submission research schemas (`src/cli/dispatch.rs:53-58,82-83,135-142`). This matches the removal instruction. The public schemas match the observed packet/submission object shapes in the exercised flow; `tests/research_handoff.rs:122-130` validates generated packets against the packet schema. Runtime validation intentionally adds byte, packet-binding, freshness and lifetime limits beyond JSON Schema (`src/research/codec.rs:77-167`, `src/research/engine.rs:475-808`); schema validity alone cannot authorize import.
- 0.1.2 improvements are materially present: subset replacement/omission warnings and caps (`src/research/engine.rs:61-115`), newly captured priority and bounded prefixes (`:573-650`), gap replacement/completion reasons (`:652-704`), receipt-first replay (`:475-539`), optional claimed `retrieved_at` (`src/research/codec.rs:100-109`, `src/research/types.rs:57-70`), offline follow-up refusal (`src/research/engine.rs:673-679`), and refresh/recovery tests (`tests/research_handoff.rs`, `tests/research_recovery.rs`). The maintained recipe is executed by `tests/skill_export.rs:322-411`; export packages release-matched files and generated command help (`src/cli/skill_export.rs:92-163`). These are local mechanics, not live host/provider qualification.
- Output and stream envelopes are governed by `schemas/output-v1.json` and `schemas/stream-v1.json`; `tests/offline_cli.rs:13-50,633-663` validates representative actual envelopes and JSONL events. The `capabilities` registry matches parser-exposed commands and the exported command reference under `tests/skill_export.rs:245-301`. There is no demonstrated generic envelope or stream schema violation in this pass. The public `run`/`run-event` schemas describe dispatcher job records, while agent research deliberately uses its separate typed `research.md` head/event fence; public research schemas cover packet/submission, not retained report/head. Agents should not assume `schema run` validates a research run record.
- The first 4096 UTF-8 bytes for newly imported or explicitly selected sources are a documented packet bound (`docs/technical/research-handoffs.md:36,42`; `src/research/inspection.rs:50-75`; `src/research/engine.rs:608-636`), not a truncation defect. A relevant restaurant/detail passage after that prefix may appear via lexical selection when query terms match, but there is no host-selected source-window option on `research run`; the documented workaround is to submit an honestly labeled excerpt as a separate source. Relevance-selected windows within the existing byte/passages ceiling would improve long-document handoffs without restoring built-in acquisition.

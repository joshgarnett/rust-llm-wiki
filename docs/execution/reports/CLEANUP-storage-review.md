## Findings requiring correction

1. **High — A saved epoch can authorize writes before independent validation.** In reviewed `src/storage/cleanup.rs:487–584`, `resume_epoch` checks epoch version/vault, writes or compares its archive, then executes `copies`, `generated`, and the supplied `marker_after`. Independent re-derivation only begins before the deletion loop at approximately `:605`. A checksum is not write authority. Trigger: interrupt cleanup, modify pending epoch and archived plan with fresh checksums to add a `Generated` entry for an absent canonical path, or change `marker_after` to another valid same-ID/schema vault marker. Resume writes those bytes before deletion eligibility can refuse anything. Existing source-deletion tamper test exercises only `deletes` and therefore misses this path. Validate the complete mutation vocabulary and bindings before *any* write: copy destinations must be the deterministic managed mapping or an exact manifest-bound immutable object; generated bytes must be deterministic exact payload maps/proofs; marker bytes must be the unique schema-only transition from the bound original marker. Preserve exact original authority rather than trusting arbitrary saved actions. **Focused test:** tamper both pending/archive, recompute checksums, add a canonical generated write and separately a marker-body alteration; require refusal with canonical tree and marker unchanged. Author accepted and is correcting; unreviewed correction.

2. **High — Interrupted cleanup does not block operational ledger mutations.** `src/vault/fs.rs:196` checks pending cleanup only in `VaultFs` mutation wrappers. `src/vault/operational.rs:548` (`append_journal`), `:592` (truncate), `:872` (`secure_replace`) and the private directory/removal primitives use `DurableIo` directly and never consult that barrier. Cleanup's held run locks prevent concurrent appends while the process lives, but an interruption releases those locks while the pending epoch remains. Direct `JobLedger` start/resume/admission and provider dispatch can then mutate history or send while migration is incomplete. Extend the barrier to operational mutation primitives, using the private storage-recovery capability only for the coordinator; preserve ordinary read/inspection. **Focused test:** interrupt before activation and after activation, release cleanup locks, attempt ledger append/admission/response-spool mutation through an ordinary handle, assert RecoveryRequired, unchanged journal/spool and zero mock sends; storage resume must still work. Author confirmed and root is integrating the operational seam.

3. **High — Missing activation metadata silently falls back to old layout.** `src/storage/layout.rs:67–85` returns `false` when `layout.json` is missing, even if WIKI.md says schema2. New record parsing accepts schema2, and normal `ChangeEngine` construction does not demand activation authority. After successful migration, losing this one file causes logical managed reads and change discovery to use now-empty legacy paths; ordinary work can proceed with hidden history excluded. The same function records but never verifies `migration_id`/`migration_hash` against the archived migration plan. Require valid format/layout/archived-plan binding for ordinary schema2 operation, with only a narrowly controlled pending-migration recovery exception for the deliberate marker-before-activation window. **Focused tests:** after completed migration, remove activation, remove archive, alter its hash/identity, or supply a checksum-valid mismatched activation; normal reads that require authority and all writes must refuse without creating fresh history. That invokes full payload loading, so the first terminal change whose undo bytes expired blocks ordinary catalog guards and later writes. Use `inspect_history` for retained terminal history, preserving its full-inspection fallback for unresolved work and the existing publication-permit observation checks. **Executed evidence read by reviewer:** root's `.artifacts/cleanup-corrections-test.log` fails `compaction_reduces_bytes_retains_undo_and_full_restore` at its post-cleanup `write_change(...).apply` (`tests/storage_cleanup.rs:72`), with `retained undo payload is unavailable after cleanup; committed history remains inspectable`. No reviewer test run was performed. Existing regression suffices after adding an ordinary catalog/context read assertion after compaction. Root notified and owns this integration seam.

5. **Medium — Raising retention later attempts to resurrect expired bytes.** `analyze` protects the newest requested number of terminal changes without considering earlier intentional expiry; `build_epoch` then insists all their payloads exist (`cleanup.rs:325–354`). Trigger: successfully clean with `retain_undo_changes=0`, then run cleanup with defaults (20), or otherwise increase the count.

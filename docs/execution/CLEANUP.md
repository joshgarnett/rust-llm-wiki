## Objective

Make lwiki useful for **agents and humans working on the same maintained wiki**. A successful research task leaves understandable, linked, cited knowledge that can be edited and refreshed. Agents should retrieve focused context and receive clear next actions. Humans should comfortably browse and edit normal Markdown. Metadata, evidence, recovery and accounting support that experience; operational files should not overwhelm it.

The owner's example had 451 visible files for six captured source revisions, one maintained page, ten extraction packets and one extraction record. Approximately 414 files were under `changes/` and `runs/`, including some useful reports. This is a count derived from the supplied tree, not a measurement of disk usage. The cleanup must address actual duplication and unbounded retention as well as visible clutter.

## Decisions and boundaries that persist

- Research is exclusively a **host-agent handoff**. The host uses its own search, fetch, MCP tools and synthesis. Do not restore CLI-side research execution or compatibility with deleted legacy research runs. Direct API graph extraction, embeddings and explicit provider probes remain supported.
- Preserve canonical Markdown knowledge, immutable source revisions, exact citation bytes, identity independent of headings, explicit graph review, author edits and freshness checks. Prefer one clear source of truth with readable projections over divergent human and machine copies.
- Preserve offline/dry-run boundaries, cumulative budgets, uncertain-charge holds, request identity and explicit retry authorization. Never silently buy repair requests or accept ungrounded model assertions to improve success rates.
- Keep hand-written provider adapters and the existing bounded transport. Responses is the recommended generation adapter; Chat Completions remains compatibility support. Do not introduce an SDK, local inference, an external database service or a CLI web-research stack as cleanup shortcuts.
- Retain Just + Bazel and six native artifact targets. Skip the sibling project's extensive dependency-verification exercise. Windows vault writes remain explicitly unsupported until a separately implemented and qualified capability exists.
- Work only on disposable vaults and mock providers locally. Existing live results are owner-reported. Do not touch real vaults, credentials, installations or publish releases during ordinary local work. Existing authorization covers coherent commits/pushes; preserve earlier tags/drafts. A next release version has not been selected by this handoff.

The product acceptance scenario is a disposable Wixom-style corpus with long restaurant roundups, repeated names, a later-section recommendation, dates, contradictory claims and one source that changes. The host agent collects material using its tools, uses lwiki handoffs, and writes readable topic/index pages with citation links and explicit gaps. A human edits a page; a later agent update preserves or reports that edit. Refresh/withdrawal identifies affected claims/pages and prevents retired evidence from appearing as current. An interrupted operation resumes safely. Replaying an import creates no duplicates. Cleanup reduces operational clutter and duplicate bytes while preserving retained knowledge, citations, accounting and permitted undo. Queries return focused evidence, and the visible vault remains understandable without reading internal event files.

For each batch, run the smallest meaningful affected regressions plus required format/lint/contract gates; root runs broader integration on a stable tree.

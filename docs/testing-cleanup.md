# Local cleanup qualification for a test agent

Use a fresh disposable vault with `WIKI.md`, a built `lwiki` from the tree under test, and loopback mock providers. Run `lwiki --json capabilities` and `lwiki --version` first, then use `lwiki schema NAME` for any machine payload. Never aim this guide at a person's vault, live credentials, paid API, or installed host. `just test` runs the repository test gate; `python3 scripts/shared_wiki_recipe.py --binary bazel-bin/lwiki` drives a separate end-to-end host simulation after `just build`. The root execution report records the exact tree and commands actually run.

For the shared human/agent case, capture a dated long Wixom roundup, a second contradictory note, and two distinct people with the same first name. Confirm the later recommendation is represented by an exact current source span, or explicitly select it with `research run --source-range SOURCE:START:END`; a quote truncated by packet bounds cannot be silently filled from memory. Inspect `graph extract` and `schema graph-resolution` before deciding identity. Create two entities only from identity evidence; preserve unresolved mentions. Review every cited assertion and its counterevidence, then apply. A packet import repeated exactly should reuse its origin without adding a second assertion set. A repeated identical source refresh should reuse its revision.

Submit a bounded host research collection and answer, inspect `research status` and the physical Markdown report under `runs/`, and keep gaps and `unassessed` labels visible. File a readable cited topic and a `pages/guide.md` navigation page with `page batch --file REQUEST.json`. Include a supporting assertion in `wiki_depends_on_ids` only after it has been accepted; raw source IDs and unassessed research claims belong in prose citations instead. Stage the batch, inspect it with `changes show`, and apply. Edit the topic directly as a simulated human, then show that the stale hash conflicts and the human text survives. Reconcile the text and submit a new guarded batch. Rename a heading and verify the stable page ID is unchanged.

Refresh the recommending source with changed facts and withdraw the counter-note. Recheck Current search/graph eligibility, `research status/report/maintenance`, and the physical report file. Historical claims and citations remain immutable while freshness reports changed support. Repair the topic and guide explicitly; leave a gap when current evidence does not justify a replacement claim. A read-only maintenance task is a prompt for the host, not an automatic semantic judgment. An interrupted apply uses `recover`; if a durable conflict persists, inspect the `changes resolve` dry-run plan and use an authorized guarded resume or abandon. Do not overwrite an unfamiliar author revision. In a disposable fault-cut fixture, interrupt after a target rename, recover, then test rollback; record whether the earlier owner's `missing retained manifest` symptom reproduces. The original vault is unavailable, so an unreproduced symptom remains unassigned rather than explained away. Exercise exhausted source/round/request/byte limits and verify actionable partial state and remaining budgets. `jobs status/amend` may extend an admitted run within its cumulative ceiling; unknown provider charges stay reserved, and a mock cannot settle real billing.

For retention, record physical file count, total logical bytes, unique-content bytes, duplicate bytes, and visible Markdown count before capture, after successful and rejected/retried mock API work, after repeat import, and after refresh. `storage inventory` reports managed classes; a separate physical filesystem count exposes visible clutter and backup overhead. Use `storage plan --retain-undo-changes 1` and `--dry-run storage cleanup` to verify no file or timestamp changes. Make a complete external copy of the vault, including `.wiki/state` and `.wiki/retained`, before guarded cleanup with `--expected-plan HASH`; check exact plan stability. After cleanup, verify old citations, receipts, unknown-charge holds, maintained pages, and a retained undo path. Restore the entire copy to a fresh directory and verify authority there. Never restore only the visible Markdown.

The focused storage fixture in `tests/storage_cleanup.rs` uses fifteen 128 KiB legacy payload copies across eight historical versions and an unrelated 2.4 MiB cache. A one-change undo window plus immutable content sharing leaves two retained objects and at least 1.5 MiB fewer retained bytes after cleanup; it does not promise that every small vault shrinks. The shared workflow reports actual before/after totals, including migration metadata and backups. The measured mock API lifecycle test covers successful/rejected/unknown-retried work, exact idempotent reuse and cleanup/accounting. Its per-operation regression bounds allow measured fixed metadata slack: 50 files/512 KiB for successful extraction+apply, 44 files/384 KiB for rejection, 24 files/256 KiB for an unknown attempt, 32 files/256 KiB for its useful retry, and zero new files/4 KiB for repeat import. These describe one bounded synthetic packet; do not infer them from the offline host recipe. A successful cross-build does not prove native crash recovery. Installed host discovery, Obsidian editing, real providers, and other operating systems remain external qualification.
